SECTION 01

Problem — the absurdity of k×n GPUs

LoRA lets every tenant fine-tune their own model cheaply. So an ML provider's job is no longer "serve one big model" — it's "serve hundreds of models that differ from each other but share a backbone." Doing that with existing serving systems is enormously wasteful.

Simply serving LoRA models as if they were independently trained from scratch wastes GPU resources. Assuming we need k GPUs to serve each LoRA model, serving n different LoRA models would seemingly require k × n GPUs. This straightforward approach overlooks something important: these LoRA models all originate from the same pre-trained model, so there is enormous weight correlation between them.

Three design guidelines

The authors argue an efficient multi-LoRA serving system must follow three guidelines. Every design decision in the paper falls out of these:

G1 · Consolidate onto few GPUs

GPUs are expensive and scarce resources, so multi-tenant LoRA serving workloads must be consolidated to a small number of GPUs, increasing overall GPU utilization.

G2 · Make batching work across models

As prior work (Orca) noticed, batching is one of the most effective approaches to consolidate ML workloads. But batching only works when requests are for the exact same model. So we need to enable batching for different LoRA models.

G3 · Only the decode stage matters

The decode stage is the predominant factor in the cost of model serving. We thus only need to focus on decode stage performance. Other aspects are less important and can use straightforward techniques (e.g. on-demand loading of LoRA weights).

The key insight: with SGMV in place, the authors observe something surprising — there are negligible performance differences between batching the same LoRA model and batching different LoRA models. At the same time, on-demand loading of LoRA models has only millisecond-level latency. Together these give Punica enormous scheduling freedom: it can consolidate user requests onto a small set of GPUs without being constrained by which LoRA models are already running on which GPUs.

Three contributions

Identifying the opportunity to batch requests across multiple, different LoRA models

A problem-framing contribution: treating multi-tenant LoRA serving as a distinct systems problem.

Designing and implementing an efficient CUDA kernel for running multiple LoRA models concurrently

That is SGMV (Segmented Gather Matrix-Vector Multiplication), the paper's technical core.

Developing new scheduling mechanisms to consolidate multi-tenant LoRA workloads

Including GPU selection logic, on-demand model loading, request migration, and a separable KvCache layout.

The result up front: with a fixed-sized GPU cluster, Punica achieves 12× higher throughput in serving multiple LoRA models compared to state-of-the-art LLM serving systems, while only adding 2ms latency per token.

SECTION 02

Background — why the decode stage

To understand why Punica is shaped the way it is, you need the arithmetic difference between the prefill and decode stages. That difference is the foundation of the entire paper.

2.1 Prefill vs. decode

A transformer LLM operates in two stages. Prefill accepts a user prompt and generates a subsequent token plus a Key-Value cache (KvCache). Decode accepts a token and the KvCache, generates one more token, and appends a column to the KvCache. Decode is iterative — the generated token becomes the input for the next step, until an end-of-sequence token is generated.

Assuming prompt length s and attention head dimension d:

Prefill: self-attention = (s, d) × (d, s) × (s, d)　　MLP = (s, h) × (h, h)
Decode:　 self-attention = (1, d) × (d, s+1) × (s+1, d)　　MLP = (1, h) × (h, h)
s = past sequence length, h = hidden dimension

The difference is stark: the decode stage's input is a single vector, so GPU utilization is low.

Fig 1 · Batching effect in the decode stage (redrawn from Figure 1 and the paper's prose).
The text gives only the batch-1 and batch-32 endpoints; the shape in between is not provided — dashed lines connect the endpoints and do not represent the real curve.

This chart is the evidence for G3. Prefill latency is proportional to batch size — the GPU's compute capability is already fully utilized, so batching buys nothing. Decode is completely different: increasing batch size from 1 to 32, decode step latency increases from 11ms to 13ms for short sequences and from 17ms to 34ms for longer ones. Batching can improve GPU utilization significantly for the decode stage — and serving latency for long output lengths is predominantly determined by decode, which is exactly what systems like Orca exploit.

2.2 The math of LoRA

LoRA's key observation is that the weight difference between the pre-trained model and the fine-tuned model has a low rank. That difference can therefore be represented as the product of two small, dense matrices.

W ∈ ℝh₁×h₂　　A ∈ ℝh₁×r　　B ∈ ℝr×h₂
W + AB is the new weight for the fine-tuned model
r is the LoRA rank, usually much smaller than the original dimension (e.g. 16 instead of 4096)

Storage overhead

0.1%–1%

Each fine-tuned model adds only this much of the model weight.

Where it applies

Usually applied to all dense projections in the transformer layer, including the Query-Key-Value-Output projections in attention and the MLP.

Note

The self-attention operation itself does not contain any weight, so LoRA never touches the attention computation core — only the linear projections around it.

So how do you serve multi-tenant LoRA efficiently on a shared cluster?

One approach is to regard each LoRA model as independent and use a traditional LLM serving system (e.g. vLLM). But this neglects the weight sharing among different LoRA models — the very thing that could significantly improve GPU efficiency. Further, treating each LoRA model as independent makes model loading time a substantial performance bottleneck when bootstrapping model serving.

Even if we share the backbone across LoRA models, one question remains: how do we batch-compute the LoRA add-ons efficiently? That is what SGMV solves.

SECTION 03

SGMV — the technical core

Segmented Gather Matrix-Vector Multiplication. Long name, one-sentence semantics: split the batch into contiguous segments, and multiply each segment by its own weight matrix.

3.1 Formalization

When a LoRA model has multiple inputs in the batch, they can be further batched together. The authors group inputs to the same LoRA model consecutively. Let n be the number of LoRA models in a batch and s_i the last element index for the i-th model within the batch, where s₀ = 0 and s_n is the batch size. Input {x_i | i ∈ [1, s_n]} is partitioned as {{x_j | j ∈ (s_{i-1}, s_i]} | i ∈ [1, n]}.

The dense projection output can then be written as:

⎡ y₁ ⎤　　⎡ x₁ ⎤　　　　⎡ x₁ ⎤
⎢ ⋮ ⎥ := ⎢ ⋮ ⎥ · W ＋ ⎢ ⋮ ⎥ · A₁B₁　　(segment 1)
⎢ y_{s₁} ⎥　⎣ x_{s₁} ⎦　　⎣ x_{s₁} ⎦
⎢ ⋮ ⎥　　　　　　　　　　　　⋮
⎣ y_{s_n} ⎦　⎣ x_{s_n} ⎦　　⎣ x_{s_n} ⎦ · A_nB_n　(segment n)
The left-hand multiplication is the backbone computation, batched through regular GEMM. The right-hand side is what SGMV must handle.

This is the fault line of the whole design. The left term x · W uses the same W for every request, so it is a standard batched GEMM — no problem. The right term multiplies each segment by a different A_i B_i — and that is precisely what existing systems cannot batch.

3.2 SGMV semantics

Note that the operator v += x·AB can be separated into two launches of the same kernel: initialize v := 0, then run v += x·A followed by y += v·B. That operator is SGMV:

Y[ s[i] : s[i+1] ] += X[ s[i] : s[i+1] ] @ W[i]
Fig 2 · SGMV semantics (redrawn from Figure 3). Requests for the same LoRA model sit in a contiguous segment; segment boundaries are described by the indptr s[].

SGMV parallelizes the feature-weight multiplication of different requests in the batch and groups requests corresponding to the same LoRA model, increasing the operational intensity of the kernel so it can use GPU Tensor Cores for acceleration.

3.3 Shrink and expand: two very different kernel schedules

The authors classify the SGMV operator into two categories based on input and output feature dimensions:

SGMV-shrink · v = x·A

The first operator in the LoRA module. It shrinks a high-dimensional input feature to a low-rank output (e.g. 4096 → 16).

Problem: the output dimension is too thin, so parallelism is insufficient.

Solution: Split-K. Split B on the input feature dimension, B = [B⁽¹⁾; …; B⁽ᵏ⁾], and dispatch different y⁽ⁱ⁾ = v·B⁽ⁱ⁾ to different threadblocks. After the partial sums finish on all threadblocks, perform a grid synchronization followed by a cross-threadblock reduction: y = Σᵢ y⁽ⁱ⁾.

SGMV-expand · y = v·B

The second operator. It expands the low-rank input feature back to a high-dimensional output (e.g. 16 → 4096).

The output dimension is wide, so parallelism is naturally abundant.

Solution: split on the output dimension. Split A on the output feature dimension, A = [A⁽¹⁾ … A⁽ⁿ⁾], dispatch different v⁽ⁱ⁾ = x·A⁽ⁱ⁾ to different threadblocks, and the concatenation of v⁽ⁱ⁾ forms the final result.

Both kernels bind the LoRA index to CUDA's blockIdx.y, so the computation on each blockIdx.y is a matrix multiplication between features and one specific LoRA weight. Both use GPU Tensor Cores to accelerate the matrix multiplication.

One important exception. When each request has a distinct LoRA index, the computation corresponding to each LoRA index degrades to matrix-vector multiplication, which is totally IO-bound. The authors designed a specific schedule for this case that maximizes memory bandwidth utilization and does not use Tensor Cores, because of the low operational intensity. This detail resurfaces when we read the source code.

3.4 Roofline analysis

The authors use the roofline model to understand SGMV's performance. FLOP and memory I/O bytes are calculated as:

FLOP = sn × hi × ho × 2
I/O　 = [ sn × (hi + ho) + n × h₁ × h₂ ] × 2
n = number of LoRA models, s = segment indices, s_n = total number of inputs, h_i / h_o = input and output dimensions of the SGMV weight matrix.
The factor 2 in FLOP comes from multiply-add; the factor 2 in I/O comes from the byte size of the 16-bit float data type.
This case study uses h_i = 16, h_o = 4096.
Fig 3 · Qualitative roofline behavior of the SGMV kernel (redrawn from Figure 7 and the paper's prose).
Axes and curve positions are illustrative — Figure 7 provides no readable raw values. Only the two ceilings (1.935 TB/s, 312 TFLOP/s) are numbers stated in the paper.
  • Distinct (every request a different LoRA): arithmetic intensity does not change, because FLOP and I/O grow at the same rate. Since each input utilizes a small amount of GPU compute units, increasing batch size increases performance (vertical on the plot).
  • Identical (all the same LoRA): the line goes up diagonally along the slope of memory bandwidth, meaning SGMV is bounded by memory bandwidth here.
  • Uniform / Skewed: in between — a combination of increasing degree of parallelism and increasing arithmetic intensity.
SECTION 04

System Design — four things beyond the kernel

SGMV only answers "how do we compute on one GPU." Punica still has to answer "how do we schedule across a cluster." The four mechanisms here — scheduling, on-demand loading, request migration, and KvCache layout — make up Punica's system layer.

Fig 4 · Punica system architecture (redrawn from Figure 2). Frontends expose a RESTful API, the scheduler dispatches requests, and each GPU server runs a runner.

4.1 Scheduling new requests

Punica's scheduler has a global view of the state of all GPUs. For each GPU, Punica maintains the working set of requests (the batch input of the LLM invocation). As new requests are added and decode steps unfold, the KvCache consumes more and more GPU memory, so Punica also continuously tracks the memory space available for KvCache on each GPU.

The scheduling rule: assign a new request to the GPU that currently has the largest working set (i.e. the largest LLM invocation batch size) while satisfying two constraints: (1) it has not reached the max batch size limit; (2) it has enough memory for the new request's KvCache. When there are multiple candidates, the one with the highest GPU UUID gets the request. When all GPUs are fully occupied (max batch size reached or insufficient memory), the request is queued. When GPUs become available, queued requests are scheduled FCFS.

The max batch size limit balances cluster throughput against per-token latency. Oversized batches greatly slow down latency while providing marginal throughput gains. The authors profile A100 GPUs and set the maximum batch size to 32.

The GPU selection logic deliberately emphasizes cluster throughput within the latency sweet spot. Its properties:

  • A busy GPU is likely to stay busy, as more requests will be assigned to it.
  • A lightly loaded GPU is likely to lower its load as requests terminate.
  • An idle GPU is likely to stay idle.

As a consequence the scheduler maintains peak throughput and consolidates GPU usage based on current overall system load, which makes scaling the cluster up and down easier. In a cloud setting, Punica performs two cluster allocation actions: (1) if no lightly loaded GPU exists, request more GPUs; (2) return the GPU resources for servers with no load.

4.2 On-demand model loading

Weight sharing between the LoRA model and the underlying pre-trained model makes model loading fast. The size of a LoRA model (matrices A and B) is only about 1% of the underlying pre-trained model.

Loading a LoRA model from main memory to GPU memory is merely an asynchronous host-to-device memory copy, bounded by PCIe bandwidth:

Load one layer

~50 µs

PCIe Gen4 x16

Load entire model

2 ms

PCIe Gen4 x16

One decode step

~30 ms

Much longer than loading → natural overlap

A pragmatic decision not to over-optimize. Since the memory copy and GPU computation can overlap, it is feasible to implement sophisticated layer-by-layer or even matrix-by-matrix loading to minimize the delay. But the authors note that each decode step takes around 30ms and each request might need thousands of decode steps. So they opted for a simpler yet equivalently efficient method: when a request is newly added to a GPU, if its LoRA model is not already loaded, issue an asynchronous memory copy to load the LoRA weight and let the GPU continue running other inputs in the batch. By the end of the model execution, the weight has already finished loading, and the new request joins the batch naturally.

4.3 Request migration

As requests generate more tokens, their KvCache occupies more GPU memory. When a GPU runs out of KvCache space, it migrates some requests to other GPUs. Migration consists of two steps — evict and add. The scheduler evicts the newest request from the GPU, which preserves FCFS semantics. Scheduling the evicted request is the same as adding a new request.

Cancel R₃

The scheduler first sends the cancellation of the request to GPU 1.

Release KvCache

After GPU 1 finishes running the previous batch, it picks up the cancellation and releases the KvCache. GPU 1 also omits R₃'s new token generated in the previous batch.

Stop streaming R₃

Stop streaming R₃'s tokens to the scheduler.

Add R₃

Immediately after sending the cancellation to GPU 1, the scheduler adds R₃ to GPU 2.

Build KvCache

GPU 2 runs a prefill step on R₃'s original prompt plus all previously generated tokens, reinstating R₃'s KvCache on GPU 2.

Start streaming R₃

GPU 2 starts to stream R₃'s new tokens to the scheduler.

Why recompute instead of moving the KvCache? The authors opt for recomputation for its simplicity. PagedAttention has shown that recomputation's latency is equal to or better than moving the KvCache in most cases, which agrees with their observation.

Punica's scheduler also supports canceling requests (a typical scenario is user disconnection); this is straightforward — remove the request from both the GPU and the scheduler states. More importantly, request cancellation as a scheduling primitive is what enables request migration.

4.4 Memory layout for KvCache

Punica uses a separable KvCache layout, which is important for text generation batching throughput. The HuggingFace Transformers library's KvCache layout consists of complicated nested lists of tensors, conceptually viewable as:

[ L , 2 , B , N , S , D ]
L = number of layers, 2 = Key and Value projection, B = batch size, N = number of heads, S = sequence length, D = head dimension

This layout has two problems:

  • Problem 1 (efficiency): in each decode step, HuggingFace Transformers concatenates one tensor along the sequence length dimension. The concatenation is inefficient as it needs to read the whole KvCache and write a new copy, whereas the new tensor is only 1/S of the KvCache.
  • Problem 2 (more serious, semantic): the batching dimension is not the outermost dimension, which means requests in the batch are hard to separate in the KvCache. Under this restriction, requests that enter the batch together need to remain together during all decode steps until all requests meet their own stopping condition.
Fig 5 · Inseparable KvCache adds wasted decode steps (redrawn from Figure 6 — an illustrative figure).
Four consecutive requests are batched together; shorter requests must run extra decode steps waiting for the longest one.

The paper notes that FasterTransformer and DeepSpeed also suffer from similar problems. Punica's KvCache layout instead is:

[ Σi ⌈ Si / P ⌉ , L , 2 , N , P , D ]
S_i = length of the i-th sequence, P = page size

They use paged KvCache (PagedAttention) to minimize memory fragmentation, and put the batching dimension on the outermost to enable continuous batching.

SECTION 05

Implementation & Source — including what the paper doesn't say

Punica's implementation has two parts: a Python library on top of PyTorch that runs on a single GPU, and system components for serving across a cluster. Beyond what the paper describes, this section quotes actual code from the punica-ai/punica repo — and there are a couple of places where it does not quite match the paper.

5.1 What the paper describes

Python library

CUDA kernels are exposed as a PyTorch Extension using PyBind11. The Llama model implementation is adapted from HuggingFace Transformers.

FlashInfer

Used for fast and memory-efficient self-attention. Besides fusing softmax(QKᵀ)V like FlashAttention, FlashInfer further supports batch decoding without padding, and supports paged KvCache.

Fused LayerNorm

110 µs → 4 µs

The authors also fuse LayerNorm, roughly a 27× latency reduction.

System components

The scheduler, frontend, and runner are all written in Rust. Unary RPC and streaming text chunks are both implemented via web socket, with I/O handled asynchronously. The runner spawns a subprocess for each GPU (a thin wrapper around the PyTorch library) and communicates via pipes.

5.2 Mixing prefill and decode in one batch

Punica mixes new requests in the prefill stage and existing requests in the decode stage in one batch. This way, dense projections and LoRA can both benefit from a bigger batch size.

For batching, all inputs are concatenated along the sequence length dimension. Prefill requests always go at the beginning, decode requests at the latter part. A BatchLen struct then distinguishes different requests: it contains a list of indices indicating the starting index of each prefill request, plus a number indicating how many decode requests there are.

In the self-attention layer, the indices and leading input states go to the BatchPrefill kernel, and the trailing input states go to the BatchDecode kernel.

A very fine scheduling touch: within a batch, the authors further organize the batch input order so that requests that share the same LoRA model are consecutive. And — the tail of prefill requests and the head of decode requests can share a LoRA model if possible. This minimizes the number of SGMV segments.

Before each batched model invocation, they concatenate batch inputs and construct BatchLen and SGMV segment indices. Both remain constant for the entire model invocation. This design avoids recomputation — otherwise BatchLen would be computed L times and SGMV segment indices 7L times (L = number of layers).

Why 7L? Because there are 7 LoRA add-ons per layer. That is very visible in the source.

5.3 Source: the seven LoRA additions per layer

Here is the attention forward from src/punica/models/llama_lora.py. Note the dense projections run as usual, then add_lora() adds the LoRA delta in place:

# src/punica/models/llama_lora.py
from punica.ops import add_lora_sgmv_custom_cutlass as add_lora

def forward(self, hidden_states, blen, prefill_kv, decode_kv,
            lora: BatchedLlamaLoraWeight):
    # 1) backbone dense projections — ordinary batched GEMM
    q_proj = self.q_proj(hidden_states)
    k_proj = self.k_proj(hidden_states)
    v_proj = self.v_proj(hidden_states)

    # 2) LoRA add-on — SGMV, accumulated in place onto q/k/v_proj
    add_lora(q_proj, hidden_states,
             lora.q.wa_ptr, lora.q.wb_ptr,
             lora.segment,          # ← this is SGMV's indptr s[]
             self.layer_idx, lora.rank)
    add_lora(k_proj, hidden_states,
             lora.k.wa_ptr, lora.k.wb_ptr, lora.segment,
             self.layer_idx, lora.rank)
    add_lora(v_proj, hidden_states,
             lora.v.wa_ptr, lora.v.wb_ptr, lora.segment,
             self.layer_idx, lora.rank)
    ...

Attention has four (q, k, v, o) and the MLP has three (gate, up, down) — 7 per layer, matching the paper's 7L. That single lora.segment tensor is the s[] from Fig 2: all the batch's LoRA scheduling information condensed into one array.

5.4 Source: the real SGMV API, and one surprise

The repo's src/punica/ops/__init__.py defines the public kernel API. SGMV's semantics match the paper exactly:

def sgmv_cutlass(y, x, w_ptr, s, layer_idx):
    """
    Semantics:
      y[s[i]:s[i+1]] += x[s[i]:s[i+1]] @ deref(w_ptr[i])

    Args:
      y: Shape: `[B, H2]`. Output vectors. Will be changed in-place.
      x: Shape: `[B, H1]`. Input vectors.
      w_ptr: Shape: `[S]`. DType: torch.int64. Pointer to the weight matrices.
      s: Shape: `[S+1]`, DType: torch.int32. Indptr of the weight matrices.
         `s[0] == 0`, `s[-1] == B`.
    """

But what the model actually uses is this hybrid:

def add_lora_sgmv_custom_cutlass(y, x, wa_ptr, wb_ptr, s,
                                 layer_idx, lora_rank):
    """
    Semantics:
      y[s[i]:s[i+1]] += x[s[i]:s[i+1]] @ deref(wa_ptr[i]).T @ deref(wb_ptr[i])
    """
    tmp1 = torch.empty((8 * 1024 * 1024,), dtype=torch.uint8, device=x.device)
    tmp2_size = _kernels.sgmv_cutlass_tmp_size(wa_ptr.size(0))
    tmp2 = torch.empty((tmp2_size,), dtype=torch.uint8, device=x.device)
    v = torch.zeros((x.size(0), lora_rank), dtype=x.dtype, device=x.device)

    _kernels.sgmv_shrink(v, x, wa_ptr, s, tmp1, layer_idx)   # ← custom CUDA kernel
    _kernels.sgmv_cutlass(y, v, wb_ptr, s, tmp2, layer_idx)  # ← CUTLASS implementation

An implementation detail the paper doesn't spell out. The shrink half (v = x·A, with the Split-K design) is the authors' own CUDA kernel. But the expand half (y = v·B) goes through CUTLASS's general implementation on the shipping path, not the custom expand schedule described in §4 of the paper.

The evidence is in the same file — the pure custom-kernel versions, sgmv() and add_lora_sgmv(), are both still stubbed:

def sgmv(y, x, w_ptr, s, layer_idx):
    if x.size(1) < y.size(1):
        raise NotImplementedError("TODO: sgmv_expand")
    ...

In other words: the expand kernel schedule the paper describes is not completed in this open-source code; CUTLASS fills that slot on the shipping path. This does not invalidate the paper's numbers (the benchmarks run this hybrid), but if you set out to reproduce the §4 expand kernel, you will not find it in the repo.

The weight memory layout reflects the hybrid directly — the comments in src/punica/utils/lora.py say it plainly:

class LoraWeight:
    def __init__(self, num_layers, in_features, out_features,
                 lora_rank, dtype, device):
        # SGMV-Shrink custom CUDA kernel uses column-major.
        self.wa = torch.zeros(
            (num_layers, lora_rank, in_features), dtype=dtype, device=device)
        # SGMV-Expand cutlass kernel uses row-major.
        self.wb = torch.zeros(
            (num_layers, lora_rank, out_features), dtype=dtype, device=device)

5.5 Source: the other kernel — BGMV

The repo contains a second kernel the paper never names, but which corresponds exactly to the §4 discussion of "each request has a distinct LoRA index": BGMV (Batched Gather Matrix-Vector), in csrc/bgmv/.

def add_lora_bgmv(y, x, wa_T_all, wb_T_all, indicies, layer_idx, scale):
    """
    Semantics:
      y[i] += (
          x[i].unsqueeze(0)
          @ wa_T_all[indices[i], layer_idx, :, :].transpose(-1, -2)
          @ wb_T_all[indices[i], layer_idx, :, :].transpose(-1, -2)
          * scale
        ).squeeze(0)

      indicies: Shape: `[B]`. Indices of the LoRA weights.
    """

Note the key difference between SGMV and BGMV. SGMV takes s (an indptr describing contiguous segments); BGMV takes indicies (one index per batch element). The former assumes requests for the same LoRA are grouped together so Tensor Cores can do matrix multiplication; the latter corresponds to the paper's "degrades to matrix-vector, totally IO-bound, does not use Tensor Cores" case — where every request is a different LoRA and there are no segments to speak of.

BGMV turned out to be quite influential: it is one of the earliest multi-LoRA batching kernel shapes adopted by downstream inference frameworks, because the indicies interface is far easier to graft onto an existing continuous-batching scheduler than SGMV's "requests must be sorted by LoRA" assumption.

Four request distributions (controlling LoRA diversity within a batch):

Distinct

Each request is for a distinct LoRA model. The hardest case.

Uniform

All LoRA models are equally popular. Given n requests, use ⌈√n⌉ models.

Skewed

Model popularity follows a Zipf-α distribution; the i-th most popular model gets α times the requests of the i+1-th. The experiments use α = 1.5.

Identical

All requests are for the same LoRA model — equivalent to traditional single-model serving.

The baseline setup is stacked against Punica, and the authors are upfront about it. Since there was no well-known multi-LoRA serving system at the time, they compare Punica against a variety of popular LLM backbone serving systems and allow various degrees of relaxation in favor of the baselines:

  • HuggingFace PEFT + HuggingFace Transformers (real LoRA support)
  • DeepSpeed (real LoRA support)
  • FasterTransformer and vLLM: run backbone-only, since these two did not support LoRA models at the time
  • And the model switching costs for baseline systems are omitted

In other words, the vLLM numbers are an idealized upper bound that pretends LoRA overhead does not exist. That makes the 12× conclusion more conservative, and more credible.

6.2 LoRA operator microbenchmark

The batched LoRA operator is implemented as two SGMV kernel launches and compared against two PyTorch baselines:

  • Loop: a for-loop over each LoRA model.
  • Gather-BMM: the gather step stacks the weight matrices each input needs into a single matrix, then torch.bmm() performs a batched matrix multiplication. Like SGMV, it launches Gather twice and BMM twice.

The authors' analysis shows Gather-BMM incurs much more I/O than SGMV: Gather reads in n × h_i × h_o elements and writes to s_n × h_i × h_o; then BMM needs to read in the s_n × h_i × h_o weight elements that Gather just wrote. In combination, Gather-BMM incurs s_n × h_i × h_o × 2 more elements of memory I/O than SGMV.

Distinct

Loop behaves terribly because it runs multiple rounds of batch size 1. Gather-BMM latency increases fast due to the slowdown of Gather. SGMV also increases gradually, from 37µs to 116µs, because batching does not change arithmetic intensity.

Uniform / Skewed

Similar to Distinct, though Gather-BMM performs slightly better (fewer matrices to load). SGMV latency increases only marginally, from 37µs to 46µs — a combination of increasing parallelism and increasing arithmetic intensity.

Identical

All implementations have the same semantics: BMM. We can therefore infer that SGMV implements BMM more efficiently than torch.bmm() in the case of LoRA. SGMV latency remains almost constant, from 37µs to 40µs.

6.4 Transformer layer benchmark

Next, layer-level performance after incorporating the LoRA operator (Testbed #1, 7B and 13B configurations, sequence lengths 512 and 2048).

Batching helps more when the sequence is shorter: at sequence length 512, latency only increases by 72% when batch size goes from 1 to 32. With longer sequences, self-attention takes more time, which reduces the layer-wise batching effect.

This is the paper's most important "non-result." In contrast to the kernel microbenchmark, layer latency is roughly the same across different workloads (Distinct / Uniform / Skewed / Identical). The reason: the computation time for the LoRA add-on is small compared to the backbone dense projection and the self-attention.

The authors italicize the consequence: this LoRA-model-agnostic performance property enables scheduling different LoRA models as if they were one model. The scheduling algorithm can then focus on overall throughput instead of individual LoRA model placement — which is exactly how Punica's scheduler is designed.

The paper's observations:

  • Punica is able to consolidate GPU usage while delivering high throughput.
  • GPUs usually run with the maximum batch size when they are not idle, because the scheduling algorithm prioritizes large batch sizes.
  • Occasionally a GPU runs with a smaller batch size because it runs out of KvCache space and migrates out a few requests to other GPUs.
  • When a GPU becomes idle (batch size = 0), it is likely to stay idle — which can then be released to the cloud provider if necessary.

SECTION 07

Discussion, Limitations & Legacy

To be clear: this paper has no Limitations section. §8 is Related Work and §9 is the Conclusion. So below I separate what the authors state from what follows from the experimental setup, rather than dressing the latter up as the authors' claims.

7.1 Positioning, as stated by the authors

Orthogonal to inference optimizations

The authors state explicitly that Punica is orthogonal to optimizations like speculative decoding. Orca's continuous batching, vLLM's PagedAttention, and FlashAttention are already integrated into Punica.

Complementary to quantization

Model and KvCache quantization save more headroom for KvCache, enabling Punica to serve longer sequences without migration. The authors note an interesting interaction: quantization reduces self-attention latency, which makes Punica's efficient LoRA kernel even more important (LoRA becomes a larger share of total latency).

Difference from PetS

PetS batches requests to different adapters (Adapters, MaskBert, Diff-Pruning, Bitfit) of an LLM on a single GPU, allowing GPU memory sharing across downstream tasks. However, it does not enable multiple different models to run concurrently.

Difference from CNN serving systems

Clipper and its successors were mainly designed for smaller CNN models. The key difference: serving CNN models is stateless, whereas LLM serving needs to persist the KvCache. That state introduces an affinity that asks for a different system design.

7.2 Limitations visible from the setup

Limitation 1: no quality or accuracy evaluation at all. The paper states LoRA models use random weights, on the grounds that weights do not affect latency performance. That is entirely reasonable for a systems paper's goals, but it means no experiment here verifies that Punica's output is numerically equivalent to serving each LoRA model individually. If you take this to production, numerical correctness is on you to validate (the repo's tests/test_sgmv.py and friends are a starting point).

Limitation 2: all LoRA models must share one rank and one backbone. All experiments use rank 16. You can see it in the SGMV interface itself — add_lora_sgmv_custom_cutlass(...) takes a single scalar lora_rank, and the weight pointer arrays wa_ptr/wb_ptr assume uniform matrix shapes. Mixed-rank multi-tenancy is out of scope.

Limitation 3: SGMV requires same-LoRA requests to be contiguous. That is the premise of the segment semantics, and it pushes complexity onto the scheduler (see §5.2's arrangement of grouping shared-LoRA requests and letting the prefill tail share a LoRA with the decode head). BGMV in the repo exists precisely as the alternative interface that sidesteps this constraint.

Limitation 4: no tables, so most baseline numbers cannot be checked. The specific values behind Figures 8, 11, and 13 are never stated in the text. For precise comparisons you would have to run the repo's benchmarks/bench_textgen_lora.py yourself.

7.3 Why this paper matters

Punica is one of the earliest works to treat multi-tenant LoRA serving as a distinct systems problem, and its technical contribution reduces to one sentence: it dismantled the apparently fundamental constraint that different models cannot be batched together, using a single kernel.

More consequential still is the §6.4 finding — the LoRA add-on is small enough relative to the backbone that layer latency is insensitive to how many distinct LoRAs are in the batch. Once that holds, the scheduling problem for multi-tenant LoRA serving collapses from "model placement" to "plain throughput scheduling," which is an order of magnitude easier. Every design in Punica's system layer stands on that result.

If you want to use this paper:

  • Building an inference framework: go straight to csrc/bgmv/ and csrc/sgmv/. BGMV's indicies interface grafts onto an existing continuous-batching scheduler far more easily than SGMV's segment interface.
  • Working on scheduling: §5.1's GPU selection logic (pick the largest working set, tie-break on highest UUID) and the "busy gets busier, idle stays idle" philosophy is a clean example of consolidation-oriented scheduling.
  • Writing kernels: Split-K plus grid sync for shrink, output-dimension splitting for expand, and falling back to an IO-bound non-Tensor-Core schedule for the distinct case — the reasoning behind those three trade-offs is worth studying.
  • Reproducing: you need A100s (80GB for the single-GPU experiments, or 2× HGX A100 40GB for the cluster ones), CUDA 11.8 or 12.1, and Python 3.10/3.11.

Conclusion

Punica's design is centered around a new CUDA kernel (SGMV) that allows batching of GPU operations for different LoRA models. For each GPU, Punica only requires a single copy of the underlying pre-trained model to serve multiple, different LoRA models, significantly improving GPU efficiency in terms of both memory and computation. Additionally, Punica's scheduler consolidates multi-tenant LoRA serving workloads in a shared GPU cluster. With a fixed-sized GPU cluster, Punica achieves 12× higher LoRA model serving throughput compared to state-of-the-art LLM serving systems while only adding 2ms latency per token.
