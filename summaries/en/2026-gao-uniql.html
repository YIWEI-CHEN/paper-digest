SECTION 01

Problem — the half that SQLite hides

Nearly every text-to-SQL benchmark runs on SQLite. But real databases are PostgreSQL, Oracle, Hive, Teradata, ClickHouse — each with its own syntax, built-in functions, type system, and execution semantics. Which leaves a basic question that has never been measured head-on: can a model express the same intent correctly across different database systems?

The SQL ecosystem is fragmented

Despite decades of standardization, the SQL ecosystem remains highly fragmented across engines. All of these systems adopt SQL-like interfaces, yet they differ substantially in syntax, built-in functions, and optimization behavior. Semantically equivalent queries frequently require dialect-specific implementations, making SQL portability a long-standing challenge in real-world data systems.

Meanwhile, LLMs have shifted data interaction from SQL-centric interfaces toward natural-language-centric ones. Users express querying intent directly in natural language, reducing the need to hand-write dialect-specific SQL. This raises the possibility of natural language as a unified interface across heterogeneous database systems — increasingly important in the era of data agents and automated analytics, where a single user request may involve querying, integrating, and operating over several different backends rather than a single one.

Existing benchmarks can't measure it

The problem is that current text-to-SQL evaluation remains largely SQLite-centric:

  • Spider (Yu et al., 2018) and BIRD (Li et al., 2023) mainly focus on SQLite execution and therefore cannot evaluate executable cross-dialect generalization.
  • Spider 2.0 (Lei et al., 2025) does introduce enterprise-level text-to-SQL workflows over different database systems, but its tasks are system-specific rather than aligned realizations of the same natural language intents across dialects. It therefore cannot isolate dialect variation from differences in schemas, tasks, or database environments.

Queries that are executable and semantically correct in one dialect may fail, behave differently, or require substantial reformulation in another — due to differences in execution semantics, function libraries, ordering behavior, implicit type casting, aggregation rules, and dialect-specific syntax. The consequence: current benchmark settings may overestimate the robustness and universality of text-to-SQL systems while overlooking their sensitivity to dialect variation.

UniQL's central design choice is alignment. Built on the BIRD development set, UniQL aligns 1,534 natural language questions with executable SQL realizations across 16 SQL dialects, yielding 24,544 dialect-specific SQL annotations. All dialects share the same natural language intents, aligned schemas, and underlying database contents — which is exactly what isolates dialect generalization from task difficulty and schema variation.

Three contributions

An aligned executable benchmark

Human-verified, aligning the same natural language intents with SQL realizations across 16 dialects. The first text-to-SQL benchmark that supports controlled cross-dialect comparison.

A hybrid SQL translation framework

Integrating tool-based translation, LLM-based translation, execution-based self-reflection, iterative translation rule evolution, and human validation.

A systematic evaluation of 13 models

Both open-weight and closed-weight LLMs, showing that current models remain far from dialect-universal — the best model solves only about half.

How this differs from dialect translation work

A related line of work studies SQL dialect translation: rule-based systems such as SQLGlot, JOOQ, and SQLines rely on manually maintained dialect mappings, while MALLET (Ngom & Kraska, 2024), RISE (Xie et al., 2026), and CrackSQL (Zhou et al., 2025) incorporate LLMs, execution feedback, or dialect-specific rules. PARROT (Zhou et al., 2026) evaluates cross-system SQL-to-SQL translation across production-grade database systems.

These efforts are complementary to UniQL, not overlapping: they focus on SQL → SQL portability, whereas UniQL evaluates whether models can directly generate executable, dialect-specific SQL from natural language under aligned cross-dialect conditions.

SECTION 02

Dataset Construction — a five-gate hybrid pipeline

Constructing a high-quality cross-dialect benchmark requires more than translating SQL strings. A translated query must be executable on the target database system and must preserve the intent of the original natural language question. UniQL's approach: an automated pipeline catches the majority, and everything it can't catch goes to humans.

Fig 1 · UniQL construction pipeline (redrawn from the paper's Figure 1). SQLite is the source dialect; the other 15 target dialects all go through this pipeline.

2.1 Database migration

Executable cross-dialect evaluation requires actually running SQL queries on real database systems, so the first step is migrating the original BIRD databases to each target system.

Although the migration aims to preserve the original schemas and values as much as possible, exact one-to-one migration is not always possible across heterogeneous DBMSs. Different systems vary in type names, identifier rules, case sensitivity, namespace organization, reserved keywords, and supported constraints. Some systems organize data through schemas or users rather than standalone database namespaces; others impose different conventions on table and column names. The authors therefore perform lightweight schema and data normalization during migration: type mapping, identifier normalization, namespace adaptation, and necessary formatting changes.

2.2 Automated translation and verification

Given an NL question x, its source SQLite query q_s, the source database D_s, and the migrated target database D_t, the goal is a target query q_t in dialect τ_t that is executable on D_t and preserves the semantics of q_s.

(1)　q_t(0) = Ftool( q_s , τ_s , τ_t )
τ_s = SQLite (source), τ_t = target dialect. A deterministic rule-based translator (SQLGlot) efficiently handles common syntactic mappings and standard SQL constructs.

The translated query is then checked through execution-based verification. Let E(q, D) denote the execution result of query q on database D. A translated query is automatically accepted only when it executes successfully on the target database and its result is equivalent to the source execution result:

(2)　V( q_s , q_t , D_s , D_t ) = 𝟙[ E(q_t , D_t) ≡ E(q_s , D_s) ]

An easily-missed design decision lives here. Standard execution accuracy in prior single-dialect benchmarks compares query outputs after converting them into unordered sets. In cross-dialect construction that introduces false positives, since ordering information and duplicate multiplicities get discarded. UniQL's automatic verification therefore preserves ordering when the query has explicit ordering semantics, and preserves duplicate-sensitive outputs in unordered comparison. This is a deliberately conservative acceptance criterion favoring precision over recall: better to wrongly reject than to wrongly accept. Rejected cases all fall through to the next gate.

If the rule-based translation cannot be automatically accepted, an LLM-based translator is invoked, conditioned on the source SQL, target schema S_t, dialect information, and the current rule set R:

(3)　q_t(1) = FLLM( q_s , S_t , τ_t , R )

When the generated query still fails equivalence verification, the model enters a bounded self-reflection loop. At iteration k, the feedback object F_k contains the previous target SQL, execution errors, or result mismatches:

(4)　q_t(k+1) = Freflection( q_s , q_t(k) , F_k , S_t , τ_t , R )

This repeats until the query is automatically accepted or the maximum number of rounds is reached. In the implementation the LLM translator is instantiated with GPT-5-mini, and each failed case is allowed up to three execution-feedback reflection rounds before being routed to later construction stages.

2.3 Iterative translation rule evolution

This is the most interesting part of the pipeline: automatic translation failures are not treated as isolated query-level errors. They are collected into a failure log and abstracted into reusable dialect transformation rules.

For each target dialect, let L_fail denote the set of failed translations after execution-guided refinement. These failures are analyzed together with the current rule set R^n and dialect documentation D_doc to produce an updated rule set:

(5)　Rn+1 = Grule( Rn , Lfail , Ddoc )
G_rule is the rule summarization process; D_doc is target-dialect documentation or tutorials.

The refined rule set is incorporated into subsequent translation attempts. This feedback loop lets the pipeline progressively handle repeated dialect-specific failures — function rewriting, type conversion, date and time operations, aggregation behavior, or system-specific syntax constraints. The authors instantiate the rule summarizer with Gemini-2.5-Pro and run rule evolution for three rounds.

The pipeline thus combines three things: the efficiency of deterministic translation, the flexibility of LLM-based rewriting, and the reusability of accumulated dialect knowledge.

2.4 Human verification

After automated translation, self-reflection, and rule refinement, the remaining cases are routed to human verification — the final quality-control stage for examples that cannot be reliably accepted by automatic execution verification. These include genuine translation failures, unsupported dialect constructs, and examples where source and target executions differ due to dialect-dependent behavior or under-specified semantics in the original SQL.

For example: different systems may return different row orders when the query does not fully specify tie-breaking, and duplicate-sensitive outputs may require semantic judgment beyond simple set comparison.

(6)　q_t* = A( x , q_s , q_t , D_t , τ_t )
q_t* is the final human-verified SQL annotation for the target dialect.

The annotation protocol: each failed case is independently reviewed by two annotators, who check both executability and semantic consistency against the original NL question and target database. If the candidate SQL is invalid, ambiguous, or not semantically equivalent, annotators rewrite it into an executable dialect-specific query. Disagreements are resolved through discussion, and the final annotation is obtained only after consensus is reached.

Overall, UniQL's construction follows a strict automatic acceptance plus human-in-the-loop verification strategy: the automatic stages efficiently resolve the majority of translations, while human verification handles long-tail cases requiring semantic judgment. This yields complete executable SQL coverage for 15 target dialects which, together with the original SQLite annotations, forms a 16-dialect benchmark.

SECTION 04

Evaluation Metric — a stricter EX than BIRD's

UniQL uses execution accuracy (EX) as its main metric, and the same execution-based protocol serves both automatic verification during construction and model evaluation during experiments. But this is not BIRD's EX.

Given a predicted SQL query q̂, the gold SQL query q*, and the database B, both are first executed on the same database:

(7)　R̂ = E( q̂ , B ) ,　　R* = E( q* , B )
If q̂ fails to execute, the prediction is marked incorrect.

Unlike BIRD-style EX implementations that convert query outputs into unordered sets, UniQL's metric preserves ordering and duplicate multiplicities when needed. For queries with explicit ordering semantics (e.g. those containing ORDER BY), outputs are compared as ordered lists:

(8)　EX( q̂ , q* ) = 𝟙[ R̂ = R* ]

This prevents a prediction with the correct rows but wrong order from being incorrectly accepted.

For unordered queries, result order is ignored, but duplicate multiplicity is still preserved. Instead of converting outputs into sets, multiset-style matching is used: each row in R̂ must be matched with and removed from R*, and the prediction is correct only if all rows can be matched exactly and no unmatched rows remain:

(9)　MultiSet( R̂ ) = MultiSet( R* )

This avoids treating outputs with different numbers of duplicate rows as equivalent.

One protocol, two stages, two roles. During construction, EX is a conservative acceptance criterion — it may reject some translations that are semantically reasonable but differ in execution results due to dialect-dependent database behavior. This is intentional: automatic acceptance favors precision over recall, and uncertain cases are routed to human verification. During model evaluation, the same protocol becomes a stricter correctness judgment, because the predicted and gold SQL are executed on the same target database system, where differences in ordering or duplicate multiplicity should be preserved rather than ignored.

Keep this in mind when reading the numbers. UniQL's EX is stricter than BIRD's set-based EX, so the SQLite scores in this paper cannot be compared directly against numbers on the BIRD leaderboard. The paper says so itself: this protocol is "stricter than the set-based EX used in some prior benchmarks."

Observation 1: stronger models perform better, but the task remains challenging

Frontier API-based models achieve the strongest overall results, with Claude-4.5-Sonnet leading on most dialects. But the best average EX is still only 54.63%, showing that UniQL exposes substantial remaining limitations even for advanced LLMs. Among open-source models, DeepSeek-v4-flash (48.12) and Qwen3-32B (47.77) obtain the strongest averages, but still leave considerable room for improvement.

Observation 2: SQLite-only evaluation hides dialect-specific weaknesses

Claude-4.5-Sonnet achieves 59.84% on SQLite and 63.75% on Oracle, but only 37.74% on Teradata. Because UniQL aligns the same intents across dialects, this gap is directly observable — and a single-dialect benchmark would miss the model–dialect interaction entirely.

Observation 3: scaling helps within model families, but doesn't erase dialect variation

The Qwen3 series exhibits a clear scaling trend: average EX increases from 33.01 for Qwen3-1.7B to 42.29 for Qwen3-4B, 44.17 for Qwen3-8B, and 47.77 for Qwen3-32B. A similar trend appears in the Llama family, where Llama-3-70B-Instruct substantially improves over Llama-3-8B-Instruct (22.04 → 39.78).

But the authors stress: scaling mainly improves overall capability rather than eliminating dialect-level variation. Difficult dialects such as Druid, Presto, and Teradata remain challenging even for larger models.

Observation 4: dialect performance reflects model familiarity as well as execution behavior

The bottom row of Table 2 shows large differences across target dialects. Oracle obtains the highest average EX (48.92), followed by SQLite, MySQL, Hive, Spark, and StarRocks, while Teradata (29.03) and Druid (29.65) are the most difficult.

But this ordering should not be read as a ranking of intrinsic dialect complexity. The authors give a sharp counter-example: Oracle is not easy to translate from SQLite in their construction pipeline (157 LLM translations + 164 reflections out of 1,534), yet models still perform strongly on it — likely because Oracle SQL has abundant public documentation, examples, and training exposure. Conversely, dialects such as Teradata and Druid may be less represented in model pretraining corpora and involve more system-specific functions, type handling, temporal operations, and execution behavior.

So UniQL reveals not only syntactic differences among SQL dialects, but also the uneven familiarity and robustness of current LLMs across database ecosystems.

SECTION 07

Cross-Dialect Consistency — the paper's most important table

The main results aggregate questions within each dialect. But because UniQL is aligned by construction, a much stricter question becomes askable: for the same intent, how many dialect realizations can a model answer correctly?

For each question, the authors count the number of dialects answered correctly (0 to 16) — cross-dialect consistency. They also report SQLite→15: the percentage of SQLite-correct questions that remain correct across the other 15 dialects.

High average execution accuracy does not imply dialect-universal correctness. Claude-4.5-Sonnet answers 8.74 dialect realizations correctly per question on average, but only 20.14% of questions are answered correctly in all 16 dialects. Gemini-2.5-Pro has a high mean of 8.34, yet its All-16 consistency is only 9.19%. Many questions are solved only partially across dialects: a model may correctly generate SQL for some database systems while failing to express the same intent in others.

SQLite correctness is not a reliable proxy for cross-dialect robustness. Even among SQLite-correct questions, only 33.66% for Claude-4.5-Sonnet and 34.29% for GPT-5-mini remain correct across all other dialects. For Gemini-2.5-Pro the ratio is only 15.38%, despite its strong average performance. Solving the SQLite realization of an intent does not guarantee that the same intent can be realized correctly in other SQL dialects.

Taken together, these two views reinforce the main observation that single-dialect evaluation is insufficient. Average EX measures performance after aggregating over dialects, while All-16 consistency asks whether a model can preserve correctness across all dialect realizations. The large gap between them shows that current models are still far from serving as dialect-universal natural language database interfaces.

A detail worth noting: Gemini-2.5-Pro ranks second on mean (8.34) but last among closed-source models on both All-16 (9.19%) and SQLite→15 (15.38%). Cross-referencing Table 2 explains why — it scores only 34.29% on Oracle, well below its own level on every other dialect. A systematic failure in one dialect is enough to gut All-16 consistency. This is exactly the failure mode only an aligned benchmark can expose.

SECTION 08

Error Analysis — failure modes are dialect-dependent

The authors conduct a post-hoc error analysis for Claude-4.5-Sonnet, the best-performing model in the main experiments, assigning each failed prediction to one of five coarse categories. The analysis is based on saved model predictions, execution errors, execution results, and manual calibration.

Syntax / function

Failures caused by invalid dialect-specific syntax, unsupported functions or operators, quoting and casting problems, or database-engine-specific execution errors.

Schema / reference

Wrong table or column references, incorrect joins, aliasing mistakes, or selecting attributes from an inappropriate relation.

Value / filter

Incorrect literals, missing or spurious predicates, NULL-sensitive conditions, boundary cases, cardinality-changing filters, tie-breaking differences.

SQL logic

Executable or nearly executable queries whose structure is semantically incomplete or incorrect: aggregation, ranking, grouping, nesting, ordering scope, or required answer columns.

Other

Rare failures that do not fit the above groups.

Three distinct failure fingerprints

Mainstream dialects → value/filter dominates

Presto, Trino, Hive, ClickHouse, Spark, SQLite, and MySQL all have value/filter as the largest category (42–49%). The model often produces plausible SQL skeletons but fails to precisely align predicates, values, joins, or output attributes.

Druid / Teradata → syntax/function dominates

Reaching 56.40% and 57.38% respectively. Failures on these systems are more strongly tied to dialect-specific functions, type handling, planner constraints, and execution behavior.

Drill → SQL logic dominates

SQL logic accounts for 47.81% — a distinct pattern where failures arise from semantically incomplete or structurally incorrect query formulations rather than surface-level syntax.

This is exactly UniQL's motivation: cross-dialect text-to-SQL robustness cannot be inferred from SQLite-only evaluation or a single aggregate accuracy score, because different database systems expose qualitatively different failure modes. A model whose SQLite failures are mostly value/filter mistakes may, on Teradata, fail more than half the time simply by not running at all.

The prediction triggers a Druid planner error: HTTP 400, INVALID_INPUT — the query could not be planned. The prediction follows the correct high-level aggregation pattern but changes NULL-sensitive filtering by removing rows with NULL enrollment or city values. The gold query instead treats NULL enrollment as 0 (NVL) and uses city-level tie-breaking — which can change the top-5 returned cities.

The prediction returns only the charter number and misses both the writing score and the ranking computation (gold uses RANK() OVER (ORDER BY AvgScrWrite DESC)), leading to an incomplete answer shape.

Even on the dialects models know best, failure isn't "can't write SQL" — it's NULL semantics, tie-breaking, and window functions, details that require precisely matching the gold semantics. UniQL's order- and duplicate-preserving EX protocol exists to surface exactly these.

Appendix B gives the three prompt templates used for construction and evaluation. Placeholders such as {dialect}, {db_details}, {question}, {evidence}, {schema}, and {error_logs} are instantiated with the corresponding database, query, and execution feedback information.

Task Overview:
You are a data science expert. Below, you are provided with
a database schema and a natural language question. Your

query to answer the question.

Database system:
{dialect}

{db_details}
This schema describes the database's structure, including
tables, columns, primary keys, foreign keys, and any
relevant relationships or constraints.

Question:
{question}

Evidence:
{evidence}

Instructions:
- Make sure you only output the information that is asked
  in the question. If the question asks for a specific column,
  make sure to only include that column in the SELECT clause,
  nothing more.
- The generated query should return all of the information
  asked in the question without any missing or extra

Take a deep breath and think step by step to find the

Notice how plain this prompt is. No schema linking, no few-shot examples, no dialect-specific hints, no self-correction loop — just one line, Database system: {dialect}, telling the model which dialect to target. That's deliberate: the authors are measuring the out-of-the-box cross-dialect capability of foundation models, not the capability of some pipeline. So the numbers here should be read as a lower bound, not as SOTA.

③ Rule summarizer — gate ④ of the construction pipeline

Corresponds to Equation (5), instantiated with Gemini-2.5-Pro and run for three rounds. It consumes the failure log and emits a reusable rule list that feeds back into ②'s {specific_rules}.

You are an expert Database Administrator and SQL Architect.
We are translating SQL queries from {source_dialect} to
{target_dialect}.
We have a list of failed translations where the translated
SQL result did not match the ground truth.

Your task is to analyze these error logs and summarize

Target {target_dialect} Schema (Reference for Exact
Table/Column Names and Types):
{schema}

Error Logs:
{error_logs}

Instructions:

Identify common patterns of failure (e.g., date formatting,
integer division, quoting rules, NULL handling, ordering
differences).
Formulate concise rules to address these failures.
The rules should be instructions for an AI translator (e.g.,
"When translating X, always do Y").
If a failure seems to be due to ambiguous logic rather than

Return ONLY the list of rules as a bulleted list. Do not

These three prompts together form a small self-improving benchmark builder. ② translates → execution verification → failures go to ③ for reflection (up to 3 rounds) → still failing, they go to ④, where ③'s failures get abstracted into rules and injected back into ②. After three rounds of that loop, whatever remains goes to humans. The pipeline's design philosophy: let automation handle generalizable failures, let humans handle failures that need semantic judgment.

What's released

Code and data are at github.com/JerryGao818/UniQL: per-dialect SQL annotations (data/queries/), schema descriptions (data/schemas/), dialect-specific executable evaluators (evaluation/), vLLM inference scripts for open-weight models (inference/), per-dialect database migration scripts (migration/), and the construction pipeline components (construction/).

But the 16 dialect databases are not downloadable as pre-built artifacts. The repo provides migration scripts and configuration files (with Docker/local setup instructions), but you must provision all 16 database systems yourself and adapt connection parameters, credentials, ports, and filesystem paths. Fully reproducing this paper is an infrastructure problem, not a modeling one.

SECTION 10

Limitations & Future Work

Everything below is explicitly stated by the authors in Section 8 — none of it is my addition.

Limitation 1: alignment costs you native data models

UniQL prioritizes controlled cross-dialect alignment: the same natural language intents, aligned schemas, and database contents preserved across 16 dialects. This design enables direct comparison across dialects, but it also limits the use of target-system-specific data models.

The migration process largely preserves the original BIRD schemas, which are SQLite-derived and mostly flat relational tables. The current benchmark therefore does not systematically cover: native features such as PostgreSQL or BigQuery JSON querying, Spark SQL and Hive complex types (arrays, maps, structs), or analytical-system features in ClickHouse and Druid for large-scale aggregation and time-series analysis.

Limitation 2: annotations favor portable formulations over dialect idioms

The SQL annotations in UniQL are designed to preserve the original query intent rather than to maximize dialect-specific idioms. A target SQL query may therefore use a portable formulation even when the target system provides a more native expression.

Future work: redesign target databases with native data models and create natural language questions that explicitly require dialect-specific capabilities — JSON operators, nested data access, array functions, partition-aware queries, or time-granularity operations. Such extensions would complement the current benchmark by evaluating not only cross-dialect portability, but also dialect-native text-to-SQL generation in real-world heterogeneous database environments.

Limitation 3: execution-based verification can't fully guarantee semantic equivalence

Even with the stricter protocol, execution-based verification cannot fully guarantee semantic equivalence between translated SQL and the original. Two queries may return the same result on the current database instance while encoding different logical conditions, especially when the database contents do not expose the difference. Different predicates, joins, or aggregation conditions may be indistinguishable on the observed data but diverge under other database instances.

UniQL mitigates this risk through conservative automatic acceptance, execution-guided checking, and human verification for ambiguous or long-tail cases. But the authors are candid: execution agreement should be understood as strong empirical evidence of equivalence on the benchmark databases rather than a complete formal guarantee.

How to use this paper

If you ship a text-to-SQL product

Table 3 is your table. Your offline score on SQLite or any single dialect has no reliable predictive power for expected accuracy on other dialects — even the best model carries only about a third of its SQLite-correct questions across the other 15. If your product talks to multiple backends, you have to evaluate each backend separately.

If you build benchmarks or evals

The EX protocol in Section 4 (order-preserving, multiset-based) is worth adopting directly. BIRD-style set-based EX accepts predictions with wrong order and wrong duplicate counts, which is a real source of false positives in cross-dialect settings.

If you build dialect translation tooling

Table 6 is a ready-made difficulty map: SQLGlot covers over 89% on MySQL, Doris, and Trino but only 54% on Teradata. And the rule-evolution move (Equation 5) — abstracting failures into reusable rules instead of patching queries one by one — is a directly portable engineering pattern.

If you want to reproduce the experiments

Budget for infrastructure first: you must provision 16 database systems yourself. The repo ships migration scripts, not pre-built instances.

Conclusion

UniQL is a human-verified benchmark for evaluating cross-dialect text-to-SQL generation, aligning 1,534 natural language intents with executable SQL realizations across 16 SQL dialects and yielding 24,544 dialect-specific annotations. Through database migration, hybrid translation, execution-guided verification, iterative rule summarization, and human validation, it enables controlled evaluation of whether models can preserve the same query intent across different database systems.

The experiments show that current LLMs remain far from dialect-universal: even strong models solve only around half of the benchmark on average, exhibit substantial variation across dialects, and often fail to transfer SQLite success to other database systems. These findings highlight the need for aligned cross-dialect benchmarks and dialect-aware text-to-SQL methods.
