-- 02 · WHY ENTERPRISE IS DIFFERENT

Four challenges public benchmarks never see

01 Schema scale

Millions of tables, 100+ columns each, constant deprecation and overlap. Picking the right table is the real problem.

02 Personalization

"Latest click-through rate" means different things to the notifications team vs. the search team.

03 Business jargon

Internal acronyms invisible to any public corpus — mined from wikis, code repos, query logs.

04 Beyond SQL

Users also want to find tables, explain queries, and debug — Text-to-SQL is only one intent.

Five indexes, one flywheel

Table / Column

From DataHub. Names, descriptions, tags, certification, deprecation. AI descriptions auto-generated when humans didn't write one. Weekly refresh.

Usage

Parsed from Trino EXPLAIN plans of successful queries → popularity & common joins. Weekly.

Table Clusters

Per-user relevant datasets via ICA (next slide). Weekly.

Example Queries

Human-authored queries from repos & wikis, auto-described then embedded.

Domain Knowledge

User-submitted in the chat UI — takes effect instantly.

Jargon Map

Wiki-sourced {jargon → explanation}, string-matched into the prompt.

Design choice: instant refresh for user contributions → contribute → improve → contribute more.

-- 07 · RESEARCHER AGENT

Hallucination isn't a bug to patch —
it's missing context

Syntax error

Trino error message → feed straight back to a fixer LLM. Cheap.

Hallucinated table / column

Means retrieval missed the right table → trigger a new retrieval round via the Researcher Agent.

  • Self-reflecting agent with tools: search tables, fetch schemas, fetch metadata.
  • Speed tuning: search on gpt-4o-mini, self-reflection on gpt-4o.
  • Custom validator catches all non-existent tables/columns in one pass — Trino only reports one error at a time.

-- 09 · EVALUATION & ABLATIONS

The knowledge graph does the heavy lifting

  • KG components drive quality: 9% → 48%.
  • Modeling components drive correctness: compile 66% → 96%.
  • Surprise: domain knowledge hurt quality (49% → 42%) — noisy records interfere.
  • Production: 53% expert-rated correct, 300+ WAU, 33% of sessions end with code in the editor.
-- 10 · NEGATIVE RESULTS (the best part)

Three academic tricks that failed in production

  • Multi-query + self-consistency — no data access means no execution to compare against, and users can't wait. Self-consistency needs input shuffling and execution.
  • Planner-LLM decomposition (DIN-SQL style) — queries became over-nested; recall and quality both dropped. gpt-4o is strong enough that decomposition only constrains it.
  • Subtasks as query expansion — no improvement in EBR table recall.

The lesson: in enterprise settings, investing in the knowledge graph and retrieval pays off more than model-side tricks.

-- 11 · TAKEAWAYS

COMMIT; -- what to remember

  • Semantics live in the knowledge graph, not the model — Score 4+ went 9% → 48% from KG components alone.
  • Treat hallucination as a retrieval failure — the Researcher Agent re-retrieves instead of just re-prompting.
  • The interface may matter more than the LLM — embed where users already work, and let them write knowledge back.

Honest caveats: 133-question eval, ~300 WAU out of a much larger company, 60-second latency. Still — the most detailed enterprise Text-to-SQL write-up we have.
